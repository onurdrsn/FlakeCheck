# FlakeCheck: How to use it

FlakeCheck connects to a GitHub repository, reads CI test results, and turns repeated failures into evidence-backed actions. This guide covers the first login, repository setup, CI integration, and the daily dashboard workflow.

## 1. First login

When the dashboard is hosted on a different domain than the API, configure the dashboard build variable `VITE_GATEWAY_URL` with the API origin, such as `https://api.example.com`. Configure the Gateway variable `CORS_ORIGINS` with the dashboard origin, such as `https://app.example.com`, then redeploy both sides. A redirect does not replace this configuration: browser API calls still need the correct origin and CORS preflight support.

1. Open FlakeCheck and sign in with your work email or GitHub.
2. After authentication, open **Connect workspace**.
3. Choose the repository type:
   - **Public repository**: enter the GitHub repository as `owner/name`. No project token is needed.
   - **Private repository**: enter `owner/name` and the repository-scoped FlakeCheck project token.
   - **Use GitHub to choose**: authorize GitHub, then select the repository and branch from the picker.
4. Click **Connect repository**.

You do not need to open **Flake Queue** first. The queue is the place to investigate results after a repository is connected.

## 2. What happens on the next visit?

After a repository is connected, FlakeCheck stores the repository access against your authenticated account and keeps the repository name in this browser for fast startup. Public and private repositories use the same saved-workspace flow; you will not be asked to choose the repository again on every page opening.

To work on another repository:

1. Open the **Repository** field in the dashboard sidebar.
2. Replace it with another `owner/name`.
3. Enter the project token if the repository is private.
4. Click **Connect**.

The repository name is persisted locally for convenience. Project tokens are not stored in browser storage; this keeps credentials out of local browser data.

## 3. Dashboard: what to open first

Start with the dashboard overview:

- **Health score**: the current reliability signal calculated from repository history.
- **Active flakes**: tests currently classified as flaky or suspicious.
- **Runner waste**: CI time spent on retries and repeated attempts.
- **Estimated cost**: calculated runner cost for the selected analysis window.

Then open **Flake Queue** (the **Flakes** section) to investigate individual tests. Select a test to view its classification, confidence, evidence payload, and recent run timeline.

## 4. Recommended daily workflow

1. Check the health score and active-flake count.
2. Open **Flake Queue** and sort through the highest-confidence findings.
3. Read the evidence and timeline before changing the test.
4. Quarantine a confirmed flake with a short reason.
5. Fix the underlying test or environment issue in GitHub.
6. Rerun CI and return to FlakeCheck to verify the result.
7. Graduate the test from quarantine when the evidence shows it is stable.

Quarantine is a safety valve, not a replacement for fixing the test. Keep the reason specific enough for the next engineer to understand the decision.

## 5. Add FlakeCheck to CI

You do not need to clone the FlakeCheck repository to use the CLI. Install the published package from npm:

```bash
npm install --global @flakecheck/cli
# Or run it without installing globally:
npx @flakecheck/cli doctor
```

To open the web dashboard from a terminal, set the hosted dashboard URL once and run:

```bash
export FLAKECHECK_DASHBOARD_URL=https://flakecheck.example.com
flakecheck server
```

For headless systems, use `flakecheck server --no-open`; the command prints the dashboard URL without launching a browser. This command opens the hosted FlakeCheck application. It does not require a repository checkout and does not start local Workers.

Run the FlakeCheck CLI after your test command and upload the test report generated by your CI tool. The report path must exist before `flakecheck ingest` runs. For local development:

```bash
pnpm --filter @flakecheck/cli run build
node packages/cli/dist/index.js init \
  --gateway http://localhost:8787 \
  --repo onurdrsn/ATS-Analyzer \
  --token "$FLAKECHECK_TOKEN"
node packages/cli/dist/index.js doctor
```

If you use a globally installed `flakecheck`, rebuild or relink it after CLI changes. Otherwise an old binary may show `RequestInit: duplex option is required when sending a body`:

```bash
pnpm --filter @flakecheck/cli run build
pnpm link --global ./packages/cli
```

Then run the complete local flow:

```bash
# Replace this with your project's real test command and report output path.
pnpm test -- --reporter=junit --outputFile=reports/junit.xml
flakecheck ingest reports/junit.xml --format junit
flakecheck analyze --window 30
flakecheck flakes
```

For a quick FlakeCheck stack check, use the checked-in fixture:

```bash
flakecheck ingest services/ingestion-service/tests/fixtures/junit.xml --format junit
flakecheck analyze
flakecheck flakes --format json
```

The fixture command is run from the FlakeCheck repository root. For another repository, use that repository's generated report path.

The exact CI command depends on the report format:

```yaml
# Example GitHub Actions shape
- name: Run tests
  run: pnpm test -- --reporter=junit

- name: Configure FlakeCheck
  env:
    FLAKECHECK_GATEWAY_URL: ${{ secrets.FLAKECHECK_GATEWAY_URL }}
    FLAKECHECK_PROJECT_TOKEN: ${{ secrets.FLAKECHECK_PROJECT_TOKEN }}
    FLAKECHECK_REPOSITORY: ${{ github.repository }}
  run: |
    flakecheck init \
      --gateway "$FLAKECHECK_GATEWAY_URL" \
      --repo "$FLAKECHECK_REPOSITORY" \
      --token "$FLAKECHECK_PROJECT_TOKEN"

- name: Send test report to FlakeCheck
  run: |
    flakecheck ingest ./reports/junit.xml --format junit
    flakecheck analyze --window 30 --fail-on-flake
```

Store the project token in GitHub Actions **Secrets**, never in the repository or workflow source. The token must be scoped to the same `owner/name` repository connected in the dashboard.

Your CI adapter should provide the commit SHA, branch, test framework, runtime/environment metadata, attempt status, duration, and report path when available. FlakeCheck uses these values to produce deterministic signatures and classifications.

## 6. CI checks to monitor

Use the dashboard after pull requests and scheduled builds to answer:

- Which tests failed more than once for the same failure signature?
- Is the failure limited to one runner or environment?
- Is the failure a regression on the current commit?
- How much runner time is being wasted by retries?
- Which tests are safe to quarantine temporarily?

Use the **Exports** area to take filtered findings back to the pipeline when you need a test skip-list or an investigation artifact.

## 7. Common issues

### “That resource could not be found.”

Make sure the dashboard is using the Gateway URL and that the local stack is running. For local development, use:

```bash
make dev
```

This starts the dashboard, Gateway, Ingestion, Analysis, and Quarantine Workers.

### A private repository is rejected

Check that:

1. The repository is written exactly as `owner/name`.
2. The project token belongs to that repository.
3. The token is passed as a CI secret and has not been copied with extra whitespace.

### The dashboard has no data

Connect the correct repository, confirm that CI has uploaded at least one supported test report, and check that the report contains test attempts with commit and environment metadata.

## 8. Security rules

- Never commit project tokens.
- Use separate repository-scoped tokens.
- Rotate a token if it is exposed.
- Do not paste secrets into issue comments, logs, or screenshots.
- Review evidence before quarantining a test.
